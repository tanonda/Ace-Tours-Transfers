C1 — VUV Currency Is Zero-Decimal: Division by 100 Creates Pricing Fraud                Severity:             CRITICAL  |             File:           mail.ts:325, payment.application-service.ts:191              The Vanuatu Vatu (VUV) is a zero-decimal currency — there are no cents. Stripe, banking systems, and financial reporting all treat VUV amounts as whole units. The codebase stores prices in &quot;VUV cents&quot; (e.g., 15000 = VT 150) but then divides by 100 in customer-facing contexts, displaying and potentially charging VT 150 instead of VT 15,000.                     EVIDENCE — mail.ts line 325:           payment.amount / 100 ${payment.currency}                     EVIDENCE — payment.application-service.ts line 191:           amount: `VT ${((booking.totalAmountCents || 0) / 100).toLocaleString()}`              If Stripe is enabled, unit_amount sent to Stripe is already divided by 100 at the display layer but passed raw (undivided) from the DB. For VUV, Stripe expects the full integer (e.g., 15000 for VT 15,000). The comment &quot;already in cents/smallest unit&quot; is wrong for VUV — it is the full vatu amount. The display emails will show customers a price 100x lower than what they will actually pay, causing chargebacks and customer panic.              Fix: Decide on a canonical unit (whole vatu is correct). Remove all /100 divisions. If you must use &quot;cents&quot; internally, document this clearly and use formatVUV(cents) = Math.round(cents) with no division.                           C2 — Session Secret Has Hardcoded Fallback — Admin Access Can Be Forged                Severity:             CRITICAL  |             File:           server/index.ts:186                     EVIDENCE:           secret: config.session.secret || process.env.SESSION_SECRET || &quot;ace-tours-secret-key-2024&quot;              validateConfig() correctly checks that SESSION_SECRET is at least 32 chars and exits if missing. However, index.ts bypasses this protection entirely by falling back to the hardcoded string &quot;ace-tours-secret-key-2024&quot; when wiring the session middleware. If SESSION_SECRET is not set in production (a deployment mistake that will happen), the app boots successfully with a publicly-known secret. Any attacker can forge valid admin session cookies.              Fix: Remove the hardcoded fallback string. Let the process.exit(1) from validateConfig() actually prevent startup. The session middleware line must be: secret: config.session.secret (no fallback).                           C3 — No Authentication on Guest Booking Lookup — Full PII Enumeration Attack                Severity:             CRITICAL  |             File:           server/routes.ts:781                     EVIDENCE:           GET /api/bookings/lookup/:bookingId  →  returns full booking + PII with NO auth check              The /api/bookings/lookup/:bookingId endpoint returns the full booking record — including customerName, customerEmail, pickupLocation, tourName, date, amount — to any anonymous caller who knows the booking ID. Booking IDs are UUID-formatted but derived from book_ + crypto.randomUUID(). While UUIDs are not sequential, they are logged in admin views, emails, and URLs. An attacker who obtains one booking reference (e.g., from a leaked email) can enumerate customer PII at scale.              Fix: Require at minimum email verification before returning full booking data. The /api/bookings/verify endpoint already implements this pattern — the lookup endpoint must be removed or consolidated into verify.                           C4 — /api/admin/bookings/reset Deletes Payment Records — Financial Record Destruction                Severity:             CRITICAL  |             File:           server/routes.ts:814, shared/schema.ts:116              The admin booking reset endpoint deletes ALL booking records by looping through storage.deleteBooking(). The payments table has bookingId as a foreign key with NO cascade delete specified, BUT the schema shows bookingItems.bookingId uses onDelete: &quot;cascade&quot;. When bookings are deleted, the associated payment audit trail is also destroyed. This violates financial record retention laws and destroys the audit trail needed to reconcile bank transfers.              Additionally, the holds associated with those bookings are not released before deletion, so tourInstance.confirmedCount and heldCount become permanently inflated with ghost numbers, corrupting future availability calculations.              Fix: This endpoint must not exist in production. If required for dev/test, gate it behind NODE_ENV === &quot;development&quot; and ensure it releases holds and retains payment records before deletion. Fix before launch or accept explicit product risk.                           H1 — Timezone Bug in Multi-Day Vehicle Booking — Wrong Dates Held                File:           CreateBookingFromCartService.ts:81                     CODE:           const startDate = new Date(item.date);  // &quot;2026-03-01&quot; → parsed as UTC midnight
currentDate.setDate(startDate.getDate() + d);  // Uses local TZ getDate()
const dateStr = currentDate.toISOString().split(&quot;T&quot;)[0];  // Converts back to UTC string              When a vehicle is booked for multiple days and the server runs in a non-UTC timezone (or even UTC+X), new Date(&quot;2026-03-01&quot;) parses as 2026-03-01T00:00:00Z. setDate() uses the local timezone&apos;s date. In UTC+11 (Pacific/Noumea, used in Vanuatu), toISOString() will return &quot;2026-02-28T13:00:00.000Z&quot; — the wrong day. Multi-day vehicle holds will be created for incorrect dates, allowing double-booking on the actual intended dates.              Fix: Parse dates as strings and do date arithmetic on strings: const d = new Date(item.date + &quot;T00:00:00Z&quot;); use d.toISOString().split(&quot;T&quot;)[0] directly after UTC-based arithmetic.                           H2 — Availability Cache is Process-Local — Stale Data Across Instances                File:           infrastructure/cache/availability-cache.service.ts              The availability cache is an in-memory Map singleton. If deployed with more than one Node.js process (PM2 cluster, Render auto-scaling, Docker replicas), each instance maintains a separate cache. A hold created on Instance A invalidates that instance&apos;s cache but not Instance B&apos;s. Instance B will return stale &quot;available&quot; counts for up to 60 seconds — the full TTL.              Under moderate traffic with 2 server instances, this is a reliable overbooking vector. Two users on different instances see available=1, both proceed, both create holds, both succeed because the DB lock (FOR UPDATE) is the true authority — but the advisory check (checkAvailability) shows phantom capacity.              Fix: This is advisory-only for the actual hold creation (which uses DB-level locks), but it causes bad UX (showing available when sold out). Replace with Redis cache or accept the advisory nature explicitly in code comments. If single-instance only, document this constraint.                           H3 — Internal Error Messages Leaked to API Clients                File:           server/routes.ts:220, 261, 300, 331, 371, 449, 479, 495, 608, 617, 702                     EXAMPLE:           res.status(500).json({ error: &quot;Failed to check availability&quot;, details: error.message })              Over 15 500-error handlers return error.message directly to the client. Database error messages from Drizzle/PostgreSQL contain schema information, table names, column names, and query structure. A malformed request that triggers a DB constraint violation will return the full PostgreSQL error string to the attacker, revealing the schema.              Fix: Log the full error server-side, return only a generic message and a correlation ID to the client. Pattern: console.error(&quot;[ERR]&quot;, correlationId, error); res.status(500).json({ error: &quot;Internal error&quot;, ref: correlationId });                           H4 — No Security Headers — XSS and Clickjacking Vulnerabilities                File:           server/index.ts, server/routes.ts (global middleware)              Zero security headers are set anywhere in the application:                   No Content-Security-Policy — XSS payloads in customerName/pickupLocation fields that reach admin UI will execute                   No X-Frame-Options — the booking form can be embedded in an attacker iframe for clickjacking                   No X-Content-Type-Options — MIME-type sniffing attacks possible                   No Strict-Transport-Security — HTTPS downgrade attacks possible                   No Referrer-Policy — booking IDs in URLs will leak to third-party analytics              Fix: Install helmet and configure it as the first middleware: app.use(helmet({ contentSecurityPolicy: { ... }, hsts: { maxAge: 31536000 } }))                           H5 — confirmSessionAtomically Uses Stale Instance Counts (Not DB-Fresh)                File:           AtomicSessionConfirmationService.ts:110-130              The atomic session confirmation loads tour instances with FOR UPDATE, which is correct. However it then uses the in-memory JavaScript value of instance.confirmedCount for the capacity check, rather than a SQL expression. Under concurrent session confirmations, this sequence is:                   T1 reads instance.confirmedCount = 8, capacity = 10, checks 8 + 2 &lt;= 10 OK                   T2 reads instance.confirmedCount = 8, capacity = 10, checks 8 + 2 &lt;= 10 OK                   T1 commits confirmedCount = 10                   T2 commits confirmedCount = 10 (was also 8 in memory, didn&apos;t see T1&apos;s update)              FOR UPDATE prevents this IF both T1 and T2 are in the same DB transaction scope. However, the code re-reads instances inside a sub-loop per instanceId, and the .for(&quot;update&quot;) is applied to a separate query — not within a guaranteed single-row lock across the two session transactions.              Fix: Use SQL arithmetic: SET confirmedCount = confirmedCount + N WHERE confirmedCount + N &lt;= totalCapacity (using a conditional update and checking affected rows). Do not rely on JS in-memory values for capacity math.                           H6 — Uncaught Exception Handler Suppresses All Errors                File:           server/index.ts:36-48                     CODE:           process.on(&quot;uncaughtException&quot;, (err) =&gt; {
  console.warn(&quot;[RECOVERY] Process continuing after uncaught exception.&quot;);
})              The global uncaughtException handler catches all exceptions and continues the process. This means a database connection failure, OOM condition, or critical internal error will be logged and silently swallowed. The application will appear &quot;up&quot; while being in a broken state — transactions will fail, bookings will silently not persist, emails won&apos;t send.              The justification (Neon library bug) should be narrowed to ONLY that specific error pattern. All other uncaught exceptions must crash the process and trigger a restart (which PM2/Render will handle). An undefined state is worse than a restart.                           H7 — Payment Webhook Endpoint Has No Signature Verification for Non-Stripe Gateways                File:           server/application/payment.routes.ts:117-130              The /api/payments/webhook/:gateway endpoint routes all non-Stripe webhooks through PaymentApplicationService.handlePaymentWebhook(). The Stripe adapter correctly verifies signatures via stripe-replit-sync. However the Manual, ANZ, BSP, and BRED adapters have handleWebhook() implementations that do nothing or just log. Any attacker can POST to /api/payments/webhook/manual with a fake paymentId and newPaymentStatus: &quot;completed&quot; to confirm any pending booking without paying.              While manual payment gateways don&apos;t currently use webhooks in this deployment, the endpoint is publicly accessible and the routing code will process any payload. This is a critical pre-auth remote booking confirmation attack.              Fix: The /api/payments/webhook/:gateway endpoint must require either a valid Stripe signature (for Stripe) or a shared HMAC secret for any future gateway. For manual gateways, the endpoint should return 405 Method Not Allowed.                           H8 — getBookingStats and getRevenueByMonth Load Entire Booking Table Into Memory                File:           server/storage.ts:409-430                     CODE:           const allBookings = await db.select().from(bookings);  // Full table scan, no LIMIT              Both getBookingStats() and getRevenueByMonth() perform unbounded SELECT * FROM bookings, load all rows into JS memory, then filter in application code. With 10,000 bookings this will cause 50-200MB memory spikes. With 100,000 bookings the admin dashboard will cause OOM crashes. Every admin dashboard load triggers both queries.              Fix: Replace with SQL COUNT/GROUP BY queries. In Drizzle: db.select({ count: sql&lt;number&gt;`count(*)` }).from(bookings).where(eq(bookings.status, &quot;confirmed&quot;)).                              PART III — MEDIUM RISK FINDINGS                           M1 — No Past-Date Validation on Booking Date                File:           server/routes.ts POST /api/bookings              No server-side check prevents bookings for dates in the past. A customer (or automated script) can create a booking for 2020-01-01. This creates phantom bookings that inflate the admin dashboard, trigger incorrect emails, and confuse availability calculations.              Fix: In CreateBookingFromCartService, validate each item.date &gt;= today (UTC).                           M2 — Zero-Pax Booking Creates $0 Booking with No Inventory Hold                File:           CreateBookingFromCartService.ts:68              If adultPax = 0 and childPax = 0, totalQuantity = 0. The code block inside if (totalQuantity &gt; 0) is skipped — no hold is created. The pricing engine returns $0. The Booking domain entity validates amountCents &gt; 0, so it will throw. But the error is thrown deep in the transaction after the booking service is called, with no clear error message to the client.              Fix: Validate (adultPax + childPax) &gt;= 1 at the route handler level with a clear 400 error.                           M3 — Hold Expiry Job Does Not Cancel Associated Bookings                File:           infrastructure/jobs/hold-expiry.job.ts              The HoldExpiryJob releases expired holds by transitioning their status to EXPIRED and decrementing heldCount on the tourInstance. However it does not find and cancel the pending bookings that referenced those holds. This leaves orphaned bookings in &quot;pending&quot; status with expired holds. When payment is later attempted for these bookings, PaymentApplicationService.initiateBookingPayment() will detect the expired hold and reject payment correctly — but the pending booking record remains forever with no cleanup path.              Fix: After releasing each hold, find bookings where holdId = hold.id AND status = &quot;pending&quot; and update their status to &quot;hold_expired&quot; or &quot;cancelled&quot;.                           M4 — AtomicSessionConfirmationService Proceeds on Expired Holds Instead of Rejecting                File:           AtomicSessionConfirmationService.ts:97-101                     CODE:           if (hold.status === &quot;ACTIVE&quot; &amp;&amp; hold.expiresAt &lt; now) {
  console.warn(&quot;Hold expired. Will attempt re-verification.&quot;);
}  // ← no throw, continues              When a hold is detected as expired within the atomic confirmation transaction, the code logs a warning and continues instead of throwing. The expired hold is then promoted to CONFIRMED status, bypassing expiry enforcement. This means a customer who takes 20 minutes between booking and payment confirmation will still have their booking confirmed even though their hold (and the capacity reservation) should have lapsed.              Fix: Throw an error when an expired ACTIVE hold is found. Do not attempt re-verification — this ambiguity creates a race window. Force the customer to re-check availability.                           M5 — Price Mismatch During Payment Confirmation Sets Status to &quot;price_mismatch&quot; With No Recovery Path                File:           BookingEventHandler.ts:62-76              When payment is confirmed but the server-side price recalculation does not match the stored booking amount (e.g., due to a price change between booking and payment), the booking is set to status: &quot;price_mismatch&quot;. The payment is marked Completed, money has been collected, but the booking is never confirmed. There is no automated admin alert, no customer notification, and no UI to handle this status. The customer has paid but has no confirmed booking.              Fix: This status must trigger an immediate admin alert email. The admin dashboard must have a dedicated view for price_mismatch bookings. Alternatively, accept the booking at the paid amount and flag for reconciliation — do not leave the customer in limbo.                           M6 — Saga Uses getPayments() Full Table Scan Every 5 Minutes                File:           BankTransferReconciliationSaga.ts:37                     CODE:           const stalePayments = await this.storage.getPayments(); // ALL payments, no filter              The bank transfer saga fetches ALL payment records every 5 minutes, then filters for overdue ones in JavaScript. This will become a performance problem at scale. There is already a getStaleProcessingPayments() method in IStorage that does a proper SQL query with index usage — it is just not used by the saga.              Fix: Replace this.storage.getPayments() with a targeted query for status IN (&quot;pending&quot;, &quot;manual_review_required&quot;) AND expiresAt &lt; NOW().                           M7 — Email Service Has No Retry or Queuing — Silent Failure on Transient Errors                File:           server/lib/mail.ts, BookingEventHandler.ts              All confirmation emails are sent inline during request processing or event handling. If the Gmail SMTP connection fails (transient network error, rate limit, credential rotation), the email send fails, the error is logged, and the booking proceeds without a confirmation email. There is no queue, no retry, and no dead letter mechanism. A customer will pay but receive no confirmation.              Fix: Implement a simple email queue (even an in-memory array processed by setInterval) with exponential backoff retries (3 attempts, 30s/120s/300s). Log permanently failed emails to a notifications table for admin review.                           M8 — Admin Booking Delete Does Not Release Holds or Invalidate Cache                File:           server/routes.ts:771              The DELETE /api/bookings/:id endpoint simply calls storage.deleteBooking(). No holds are released, no tourInstance counts are decremented, and the availability cache is not invalidated. Deleting a confirmed booking leaves the tourInstance with an inflated confirmedCount permanently, making future availability checks return false negatives (showing fully booked when capacity is actually available).              Fix: Before deleting a booking, check if it is confirmed and if so decrement confirmedCount. Release any associated holds. Invalidate the availability cache for the booking&apos;s tour and date.                           M9 — CORS Not Configured — Any Origin Can Make Credentialed API Requests                File:           server/index.ts (global middleware stack)              No CORS middleware is configured. In Express without CORS headers, the browser&apos;s default same-origin policy applies — which might be acceptable for a single-domain deployment. However, if the API is ever accessed from a different subdomain, a mobile app, or a third-party partner integration, requests will either fail or (worse) succeed with credentials from any origin. Combined with no helmet, this creates a broad attack surface.              Fix: Add cors() middleware with explicit origin whitelist. For this deployment: origin: [process.env.APP_URL].
